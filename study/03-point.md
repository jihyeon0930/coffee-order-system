# 포인트 결제 및 동시성 제어 학습 노트

# 이번 이슈에서 구현한 기능

- 사용자 생성과 조회
- 포인트 충전과 잔액 조회
- 포인트 정상 차감과 잔액 부족 예외 처리
- JPA 비관적 쓰기 락을 이용한 동일 사용자 포인트 동시성 제어
- 정상 흐름, 예외 흐름, HTTP API, 실제 멀티 스레드 동시성 테스트

주문 도메인은 아직 구현되지 않았으므로 이번 Issue에서는 주문 자체를 만들지 않았다. 대신 다음 주문 서비스가 같은 트랜잭션 안에서 호출할 수 있도록 `PointService.use(memberId, amount)`를 구현했다.

## 왜 필요한 기능인가

포인트는 주문 결제에 사용하는 금전성 데이터다. 두 요청이 같은 잔액을 동시에 읽고 각각 차감하면 잔액 부족 검증을 모두 통과하거나, 한 요청의 변경이 다른 요청을 덮어쓰는 문제가 생길 수 있다.

예를 들어 잔액이 1,000이고 700 차감 요청 두 개가 동시에 실행된다고 가정한다.

1. 트랜잭션 A가 잔액 1,000을 읽는다.
2. 트랜잭션 B도 잔액 1,000을 읽는다.
3. A와 B 모두 `1,000 >= 700`이라고 판단한다.
4. 둘 다 차감을 승인하면 총 1,400을 사용한 셈이 된다.

DB의 단순 UPDATE만 사용한다고 이 문제가 자동으로 해결되지는 않는다. 조회, 잔액 검증, 변경이 하나의 원자적 임계 구역으로 보호되어야 한다.

## 사용한 기술

| 기술 | 사용 목적 |
| --- | --- |
| Spring Data JPA | 회원 저장과 잠금 조회 |
| `@Lock(PESSIMISTIC_WRITE)` | 같은 회원 행에 대한 배타 락 획득 |
| `@Transactional` | 잠금 조회, 검증, 변경, 커밋을 하나의 작업으로 묶음 |
| JPA Dirty Checking | 엔티티 메서드로 변경한 잔액을 커밋 시 UPDATE |
| H2 MySQL mode | 외부 DB 없이 Repository와 동시성 흐름 검증 |
| `CountDownLatch` | 여러 테스트 스레드의 시작 시점을 맞춤 |
| `ExecutorService` | 실제 병렬 차감 요청 실행 |

## 핵심 코드 설명

### 포인트 규칙을 엔티티에 둔 이유

```java
public void use(long amount) {
    validatePositiveAmount(amount);
    if (pointBalance < amount) {
        throw new BusinessException(ErrorCode.POINT_NOT_ENOUGH);
    }
    pointBalance -= amount;
}
```

잔액이 음수가 될 수 없다는 규칙은 포인트 상태를 가진 `Member`가 직접 지킨다. Service가 필드를 계산해 setter로 넣는 구조보다 잘못된 상태를 만들기 어렵고, 주문 외의 다른 기능에서 포인트를 사용해도 같은 규칙이 적용된다.

### 비관적 락 Repository

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("select m from Member m where m.id = :memberId")
Optional<Member> findByIdForUpdate(@Param("memberId") Long memberId);
```

Spring Data JPA는 이 메타데이터를 EntityManager의 잠금 모드로 전달한다. 데이터베이스는 일반적으로 `SELECT ... FOR UPDATE` 형태로 실행해 대상 행에 배타 락을 건다. 먼저 락을 얻은 트랜잭션이 끝날 때까지 같은 행을 쓰기 잠금으로 조회하는 다음 트랜잭션은 기다린다.

### 트랜잭션 범위

```java
@Transactional
public PointResponse use(Long memberId, long amount) {
    Member member = findMemberForUpdate(memberId);
    member.use(amount);
    return PointResponse.from(member);
}
```

`@Transactional`은 Spring AOP 프록시를 통해 동작한다. 외부 객체가 `PointService.use()`를 호출하면 프록시가 트랜잭션을 시작하고 실제 메서드를 실행한다. 잠금 조회 후 반환된 엔티티는 영속성 컨텍스트가 관리하며, 커밋 직전에 변경 감지로 UPDATE가 실행된다. 커밋 또는 롤백이 끝나면 DB 락도 해제된다.

따라서 잠금 Repository 호출만 별도 메서드에 두고 트랜잭션 밖에서 잔액을 변경하면 안 된다. 잠금을 얻는 시점부터 검증과 변경이 끝날 때까지 하나의 트랜잭션이어야 한다.

### 동시성 테스트

초기 포인트 1,000에 대해 20개 스레드가 동시에 100씩 차감한다. 올바른 구현이라면 정확히 10건만 성공하고 나머지 10건은 `POINT_NOT_ENOUGH`로 실패해야 한다.

검증 항목은 다음과 같다.

- 성공 요청 수는 10개인가
- 잔액 부족 실패는 10개인가
- 최종 잔액은 0이며 음수가 아닌가
- `성공 횟수 × 차감액 + 최종 잔액 = 최초 잔액`인가

마지막 식은 한 변경이 다른 변경을 덮어쓰는 lost update와 중복 성공을 함께 확인한다.

## 오늘 새롭게 배운 내용

### 왜 비관적 락을 선택했는가

포인트 결제는 충돌이 발생했을 때 사용자에게 낙관적 락 예외를 그대로 반환하기보다, 먼저 들어온 요청부터 최신 잔액을 확인해 확정적으로 처리하는 것이 이해하기 쉽다. DB 행 락은 애플리케이션 서버가 여러 대여도 모두 같은 DB를 기준으로 직렬화할 수 있다.

비관적 락의 대가는 대기 시간과 처리량이다. 트랜잭션이 길면 다른 요청이 오래 기다리고, 여러 행을 서로 다른 순서로 잠그면 교착 상태가 생길 수 있다. 그래서 이번 구현은 한 회원 행만 잠그고 외부 API 호출 없이 검증과 변경을 즉시 끝낸다.

### 낙관적 락과의 차이

낙관적 락은 엔티티에 `@Version` 필드를 두고 UPDATE 시 버전이 같은지 확인한다. 실제 DB 락을 오래 유지하지 않아 충돌이 드문 환경에서 처리량이 좋다. 하지만 충돌하면 `OptimisticLockException` 계열 예외가 발생하므로 재조회와 재시도를 직접 설계해야 한다.

| 기준 | 비관적 락 | 낙관적 락 |
| --- | --- | --- |
| 충돌 처리 | 먼저 락을 획득한 트랜잭션 뒤로 대기 | 커밋 시 버전 충돌로 실패 |
| 적합한 상황 | 충돌 가능성이 높고 즉시 정합성이 중요 | 충돌이 드물고 읽기가 많음 |
| 장점 | 처리 흐름이 직관적이고 다중 서버에 적용 가능 | DB 락 대기가 적고 처리량에 유리 |
| 단점 | 락 대기, 타임아웃, 교착 가능성 | 재시도 정책과 멱등성 설계 필요 |

### `synchronized`를 사용하지 않은 이유

`synchronized`는 한 JVM 안의 스레드만 제어한다. 서버 인스턴스가 두 대라면 각 서버가 서로 다른 모니터 락을 가지므로 같은 회원 요청을 동시에 처리할 수 있다. DB 비관적 락은 모든 서버가 공유하는 회원 행을 기준으로 동작하므로 다중 서버에서도 유효하다.

### `@Transactional`이 필요한 이유

- 잠금의 생명주기를 트랜잭션 종료까지 유지한다.
- 잔액 조회, 검증, 차감을 하나의 원자적 작업으로 만든다.
- 예외 발생 시 변경을 롤백한다.
- 영속 상태 엔티티의 변경을 Dirty Checking으로 저장한다.

Spring의 기본 트랜잭션은 unchecked 예외인 `BusinessException` 발생 시 롤백된다. 잔액 부족 예외가 발생하면 UPDATE 없이 트랜잭션이 종료되고 락이 해제된다.

## 어려웠던 점

동시성 테스트는 여러 작업을 제출하는 것만으로 동시에 시작된다고 보장할 수 없다. 실행 시점이 크게 어긋나면 락이 없어도 우연히 테스트가 성공할 수 있다. 또한 최종 잔액만 확인하면 중복 성공이나 갱신 유실을 충분히 설명하지 못한다.

테스트 DB인 H2의 락 동작은 운영 MySQL과 세부 구현이 다를 수 있다. 테스트는 JPA 잠금 흐름과 애플리케이션 정합성을 빠르게 검증하지만, 운영 전에는 MySQL Testcontainers 통합 테스트로 보완하는 것이 좋다.

## 어떻게 해결했는가

- `ready` latch로 모든 작업이 출발 준비를 마칠 때까지 기다렸다.
- `start` latch를 한 번에 열어 요청 시작 시점을 최대한 맞췄다.
- 각 Service 호출이 Spring 프록시를 거치게 하여 스레드마다 독립 트랜잭션을 사용했다.
- 성공 수, 잔액 부족 수, 최종 잔액, 보존 식을 모두 검증했다.
- 충전과 차감 모두 같은 잠금 조회를 사용해 동시 갱신 유실을 방지했다.

- 주문 저장과 포인트 차감을 하나의 트랜잭션으로 결합하는 방법

## 면접에서 나올 수 있는 질문과 답변

### Q1. 비관적 락을 선택한 이유는 무엇인가요?

A. 포인트는 금전성 데이터이고 동일 회원에 동시 결제 요청이 들어올 수 있습니다. 충돌 시 실패 후 재시도보다 DB에서 같은 회원 행을 순차 처리하는 편이 정합성 규칙과 구현이 명확했습니다. 모든 서버가 같은 DB 행을 잠그므로 다중 인스턴스 환경에서도 동작합니다.

### Q2. 비관적 락과 낙관적 락의 핵심 차이는 무엇인가요?

A. 비관적 락은 충돌할 것이라고 보고 먼저 DB 락을 획득합니다. 낙관적 락은 충돌이 드물다고 보고 락 없이 처리한 뒤 버전으로 충돌을 검출합니다. 전자는 대기와 교착 비용이 있고, 후자는 충돌 시 재시도와 멱등성 설계가 필요합니다.

### Q3. 왜 `@Transactional`이 없으면 안 되나요?

A. 비관적 락은 트랜잭션 범위에서 유지됩니다. 트랜잭션이 없거나 잠금 조회 직후 끝나면 잔액 검증과 변경 전에 락이 풀릴 수 있습니다. 조회, 검증, 변경, 커밋을 하나의 경계로 묶어야 합니다.

### Q4. `synchronized`로 해결하면 안 되나요?

A. 단일 JVM에서는 가능하지만 서버가 여러 대면 각 JVM의 락이 독립적입니다. DB 락은 모든 인스턴스가 공유하는 자원을 기준으로 제어하므로 현재 구조에 더 적합합니다.

### Q5. 비관적 락의 단점과 대응 방법은 무엇인가요?

A. 락 대기로 응답이 느려지고, 잠금 순서가 엇갈리면 교착이 발생할 수 있습니다. 트랜잭션을 짧게 유지하고, 여러 행을 잠글 때 정렬된 동일 순서를 사용하며, 락 타임아웃과 제한된 재시도 정책을 둡니다.

### Q6. 이 테스트가 중복 차감을 막았다고 어떻게 판단하나요?

A. 1,000포인트에 100포인트 차감 20건을 동시에 실행했을 때 정확히 10건만 성공해야 합니다. 성공 수와 실패 수뿐 아니라 최종 잔액과 `성공 수 × 차감액 + 최종 잔액 = 초기 잔액`도 검증해 중복 성공과 갱신 유실을 확인했습니다.

### Q7. 비관적 락만으로 같은 주문 요청의 재전송까지 막을 수 있나요?

A. 아닙니다. 비관적 락은 동시에 잔액을 갱신할 때 정합성을 보장하지만, 같은 주문 요청이 시간차를 두고 재전송되면 별개 요청으로 차감될 수 있습니다. 주문 Issue에서는 주문 요청 ID나 결제 키에 unique 제약을 두는 멱등성 설계가 추가로 필요합니다.
